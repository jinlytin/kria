# Kria 工作台

Kria 是使用 SwiftUI 与 AppKit 构建的 macOS 原生效率工具集合，目前包含「批量访问」和「随机闹钟」两个模块。

批量访问提供类似 Postman 的请求工作区：管理请求、双向编辑 cURL、单次发送或批量调度，以及查看响应内容。工作台是统一安装的功能集合包：批量访问内嵌于工作台应用中，运行时使用独立进程和 Dock 图标，无需另外安装组件。本文说明当前已实现的功能、界面设计、实现方式与使用注意事项。

## 1. 环境与启动

### 运行与开发要求

- macOS 15.6 或以上，部署版本由 `kria.xcodeproj/project.pbxproj` 指定。
- 日常使用只需安装完整的 `KriaWorkbench.app`，无需单独安装批量访问，也无需安装 Xcode。
- 从源码编译需安装完整 Xcode，并完成首次启动配置和许可协议确认。工程创建工具版本为 Xcode 26.2，建议使用该版本或兼容的更新版本。
- 使用系统内置的 SwiftUI、AppKit、Combine、Foundation；当前没有第三方包依赖。
- 批量访问执行器调用系统的 `/usr/bin/curl`；组件图标构建阶段使用 Xcode 的 `swiftc` 和系统的 `/usr/bin/iconutil`，使用者不需要自行生成图标。
- 当前 IDE 启动任务面向 Apple Silicon（`arm64`），Xcode 默认安装路径为 `/Applications/Xcode.app`。

### 单包安装与组件运行

- 对外安装或复制的单位是整个 `KriaWorkbench.app`。批量访问位于它的 `Contents/Helpers/KriaBatchAccess.app`，不是需要额外下载的插件。
- 构建 `KriaWorkbench` 时会自动构建批量访问目标，并将组件复制进工作台包；组件设置 `SKIP_INSTALL = YES`，不作为另一个顶层应用单独安装。
- 安装时将完整工作台应用复制到「应用程序」目录，保留包内结构，不要只复制可执行文件或单独移出组件。
- 打开工作台后点击批量访问卡片的「使用」，Dock 中会分别显示工作台与「Kria 批量访问」。重复打开组件会复用已有进程，并激活或还原其最小化窗口。
- 退出批量访问不会退出工作台；退出工作台也不会自动退出已打开的批量访问。随机闹钟仍由工作台进程管理，不是独立 Dock 应用。
- 打包分发仍需另行完成签名、公证及目标架构配置；下面的关闭签名构建命令仅用于本地开发，不表示已经完成正式分发。

### 在 CatPaw IDE 中一键启动

1. 打开仓库根目录。
2. 按 `⌘⇧B`，执行默认任务「Kria：编译并启动」。
3. 编译成功后自动打开 `KriaWorkbench.app`。
4. 在工作台中点击「批量访问」卡片的「使用」按钮打开请求工作区。

任务配置在 [`.vscode/tasks.json`](.vscode/tasks.json)，执行顺序为「编译工作台 → 启动应用」。构建产物位于 `build/Build/Products/Debug/KriaWorkbench.app`。

启动任务使用普通 `open`，重复执行会激活已有工作台实例，不会自动替换运行中的代码。更新代码或图标后，应先退出批量访问和工作台，再编译启动，避免仍在查看旧进程。组件启动同样不创建额外实例。

### 在 Xcode 中启动

1. 打开 `kria.xcodeproj`。
2. 选择 `KriaWorkbench` Scheme 和本机 macOS 运行目标。
3. 使用 `⌘R` 编译运行。

| 目标 | 用途 | Bundle ID |
| --- | --- | --- |
| `KriaWorkbench` | 工作台主应用；统一安装包及日常开发启动入口 | `childe.kria.workbench` |
| `KriaBatchAccess` | 工作台内嵌的批量访问应用；独立进程及 Dock 身份 | `childe.kria.batchaccess` |
| `kria` | 框架目标，不是应用启动入口 | `childe.kria` |

正常开发选择 `KriaWorkbench` Scheme 即可，无需分别编译或安装组件。

### 在终端中启动

在仓库根目录执行：

```bash
DEVELOPER_DIR=/Applications/Xcode.app/Contents/Developer \
xcodebuild -quiet \
  -project kria.xcodeproj \
  -scheme KriaWorkbench \
  -configuration Debug \
  -destination 'platform=macOS,arch=arm64' \
  -derivedDataPath build \
  CODE_SIGNING_ALLOWED=NO \
  build
```

编译成功后执行：

```bash
open build/Build/Products/Debug/KriaWorkbench.app
```

这些参数用于本地开发，不等同于签名、公证或分发流程。Intel Mac 需要相应调整运行目标架构；Xcode 安装位置不同时，需要同时修改开发目录与 IDE 任务中的命令路径。

需要 Release 产物时，将 `-configuration Debug` 改为 `-configuration Release`；完整应用位于 `build/Build/Products/Release/KriaWorkbench.app`，包内同样包含批量访问组件。`build/` 已被 Git 忽略，不应将编译缓存、临时图标导出器或生成的应用包提交到仓库。

## 2. 批量访问功能

### 2.1 请求管理

- 导入单条 cURL 命令，自动创建并选中一个请求记录；导入本身不会发送请求。
- 支持直接粘贴或从剪贴板导入，也可以新建空白请求。
- 多行命令支持反斜杠续行及 LF、CRLF、CR 等换行形式；兼容粘贴内容中的空行、不换行空格（NBSP）缩进，以及未加引号区域中续行符后的空白，不会将续行换行误判为第二条 URL。
- 兼容处理只针对词法分隔与续行，不会全局替换引号内的内容。单引号内的 Body、Cookie、签名头和 JSON 文本按字面量保留，Query 在未修改时保留原始编码。
- 导入请求的默认名称取 URL 的 path，不包含域名、query 或 fragment；无 path 时使用 `/`。
- 例如 `https://example.com/api/users?page=1` 的默认名称为 `/api/users`。
- 点击请求编辑区顶部的名称可手动重命名；修改 URL 不会覆盖导入时设置的名称。
- 支持按名称、URL 或请求方法搜索。
- 左侧请求的右键菜单支持复制、删除；删除需要确认，也会取消该请求正在执行的任务。
- 每个请求拥有独立配置和本轮响应记录。

### 2.2 请求编辑与 cURL 双向同步

中间编辑区支持：

| 区域 | 功能 |
| --- | --- |
| 地址栏 | 编辑 HTTP 方法与 URL；点击「发送」或在 URL 输入框中回车进行单次发送 |
| Params | 增删、修改、启用或禁用 Query 参数 |
| Headers | 增删、修改、启用或禁用请求头 |
| Body | 无 Body、Raw、x-www-form-urlencoded、仅文本 form-data |
| 设置 | 跟随重定向、压缩响应、忽略 TLS 证书校验；查看保留的额外 cURL 参数 |
| 批量执行栏 | 配置频率、时长、调度方式，启动批量执行并查看状态 |

右侧 cURL 编辑区支持修改、格式化和复制命令：

- 修改 cURL 后自动解析并更新中间预览。
- 修改中间的 URL、参数、Headers、Body 或设置后，自动重新生成 cURL。
- 编辑过程中引号未闭合、参数不支持或 URL 无效时，显示错误并保留上次有效预览，发送功能禁用。
- 结构化编辑器中的禁用字段不会参与实际发送，并尽可能在 cURL 同步过程中保留。
- Raw Body 按文本发送；发送 JSON 时应配置 `Content-Type: application/json`。导入 `--json` 会补充相应 JSON 请求头。

### 2.3 单次发送与批量调度

- 「发送」仅发送一次；批量栏中的「执行」按配置创建本轮调度任务。
- **脉冲**：每个计划秒的起始时刻调度该秒的请求。
- **每秒内随机**：为每个请求生成该计划秒内的随机发送时刻，再按时间排序执行。
- 每个请求记录的一轮执行最多同时运行 32 个请求；不同请求记录可以各自执行，32 不是所有记录共享的全局限制。
- 点击地址栏旁的「停止」会取消未发出的任务，并终止正在运行的 cURL 进程。
- 每次启动单次或批量执行都会清空该请求上一轮响应记录，只保留本轮结果。
- 执行采用发送时的请求快照，运行中修改配置只会影响下一轮。
- 超时、取消、cURL 非零退出码以及非 2xx HTTP 状态会被标记为失败。

配置边界：

| 项目 | 当前规则 |
| --- | --- |
| 默认频率 | 10 次/秒 |
| 默认时长 | 3 秒 |
| 频率范围 | 1–1000 次/秒，整数 |
| 时长范围 | 1–3600 秒，整数 |
| 单批计划请求数 | 频率 × 时长，最多 10000 次 |
| 并发上限 | 每个请求记录的一轮执行最多 32 个 |
| 单次请求超时 | 从 cURL 进程启动起最多 15 秒，包含重试等待 |

批量「时长」表示调度时间范围，不是整轮完成的硬截止时间。当请求较慢或达到并发上限时，发送可能延迟；调度结束后还需要等待正在运行的请求完成。实际 QPS 不保证等于配置频率，cURL 自身的重试也可能增加实际网络调用次数。

### 2.4 响应查看

- 显示 HTTP 状态、耗时、响应大小、开始与结束时间。
- 支持 Body、Headers 和「批量记录」三个标签页。
- 点击批量记录可查看该次调用的完整可展示内容，也可切回最新响应或清空记录。
- 响应正文从左上角开始显示；整个文本区域可点击聚焦，支持拖选、全选和复制。
- Pretty 模式下，有效 JSON 显示语法高亮、行号和节点展开/折叠按钮。
- 左侧操作栏使用独立浅灰背景和分隔线；横向滚动正文时侧栏固定，纵向滚动时与节点对齐。深色模式下使用对应背景和分隔色。
- 默认展开前两层；菜单支持展开全部、折叠全部、仅展开两层。
- 右键支持复制节点原始 JSON；工具栏复制 Pretty 响应时包含被折叠的子节点，不会只复制省略号。
- Raw 模式显示未格式化文本。非 JSON、超出解析边界或附有执行错误提示的正文回退为普通文本。

## 3. 界面设计

工作区采用三栏结构，优先给常用的请求编辑和响应查看分配空间：

| 位置 | 内容 | 初始布局 |
| --- | --- | --- |
| 左侧 | 请求集合、搜索、复制与删除入口 | 可拖动调整宽度 |
| 中间上方 | 名称、地址栏、批量执行栏、请求字段编辑 | 中间可用高度的 50% |
| 中间下方 | 状态摘要、响应正文、响应头、批量记录 | 中间可用高度的 50% |
| 最右侧 | cURL 双向编辑、解析提示 | 整个工作区宽度的 1/6，约 16.7% |

- 批量执行栏位于请求地址正下方、请求字段标签栏上方。
- 请求与响应区使用显式高度计算，而不是按内容的理想尺寸分配。参数过多时在编辑区内部滚动，不会挤压响应区；首次响应返回也不会改变比例。
- 上下分隔线支持拖动；新建、导入或切换请求时，中间区域以 50:50 初始化。
- cURL 的左右分隔线支持拖动，切换请求时保留当前宽度比例；窗口缩放时按所选比例重新计算。
- 分栏设置仅在当前窗口会话中保留，不写入请求持久化文件。
- 最小尺寸保护：请求区通常至少 300 pt、响应区至少 220 pt；cURL 区通常至少 160 pt，左侧加中间区域至少 720 pt。达到最小尺寸约束时，实际比例可能与所选比例不同。

### 统一图标与色调

- 工作台的批量访问卡片、组件内部标题栏、运行时 Dock 图标与应用包 `.icns` 共用 `BatchAccessIcon.swift` 的绘制逻辑，仅展示尺寸不同。
- 图形为橙色圆角方形、白色圆环及居中的竖向闪电。闪电采用略加宽的瘦长轮廓，设计坐标宽 58、高 96，保持圆环内留白。
- 图标背景和组件强调色共用 sRGB 常量 `(0.94, 0.38, 0.17)`，约为 `#F0612B`；工作台自身的头像图标不受组件图标调整影响。
- 圆环与闪电使用明确的 Core Graphics 路径绘制，不依赖 SF Symbol 的分层或调色板渲染，避免闪电细节丢失为白色圆点。

## 4. 核心实现方式

### 4.1 分层结构

模块采用 View / ViewModel / Service 分层：

| 文件 | 职责 |
| --- | --- |
| `kria/kriaApp/KriaWorkbenchApp.swift` | 工作台 SwiftUI 入口；按编译条件切换批量访问 AppKit 入口、菜单、Dock 图标及退出流程 |
| `kria/kriaApp/WorkbenchView.swift` | 工作台与主窗口外观 |
| `kria/components/batchAccess/batchAccess.swift` | 功能卡片、内嵌组件启动、请求工作区、导入弹窗、分栏布局与 cURL 编辑区 |
| `kria/components/batchAccess/BatchAccessIcon.swift` | 统一强调色、图标路径、多分辨率渲染及构建期 iconset 导出 |
| `kria/components/batchAccess/viewModels/BatchAccessViewModel.swift` | 请求状态、双向同步、批量调度、取消和本地持久化 |
| `kria/components/batchAccess/services/CurlRequest.swift` | 请求模型、cURL 词法解析与序列化、参数校验、记录模型 |
| `kria/components/batchAccess/services/CurlCommandRunner.swift` | cURL 子进程执行、超时、取消和响应读取 |
| `kria/components/batchAccess/services/JSONResponseDocument.swift` | 保留原始字面量的 JSON 树解析及可见行生成 |
| `kria/components/batchAccess/views/BatchRequestEditorView.swift` | 请求地址、字段、Body、批量参数与状态 |
| `kria/components/batchAccess/views/BatchResponseView.swift` | 响应标签页、记录选择、JSON 准备与复制操作 |
| `kria/components/batchAccess/views/ResponseTextEditor.swift` | AppKit 只读文本视图、语法高亮和独立节点操作侧栏 |
| `kria.xcodeproj/project.pbxproj` | 目标配置、组件构建依赖、图标生成与组件内嵌阶段 |
| `kria.xcodeproj/BatchAccess-Info.plist` | 组件专用基础元信息，声明 `CFBundleIconFile = BatchAccessIcon` |
| `.vscode/tasks.json` | IDE 编译及启动任务 |

`BatchAccessViewModel` 在主 Actor 上维护 UI 状态；cURL 阻塞等待运行在后台队列，批量请求通过任务组调度。JSON 解析在后台任务中进行，过期解析结果不会覆盖当前响应。

### 4.2 cURL 解析与执行

- `CurlRequestParser` 使用类似 Shell 的词法规则支持引号、转义和多行续行，但不执行 Shell。换行判断使用 `Character.isNewline`，兼容 Swift 将 CRLF 视为单个 Character 的情况；未加引号区域允许续行反斜杠与换行之间有空白。
- 结构化模型保存方法、URL、Query、Headers、Body、开关及允许保留的额外选项，再生成参数数组或 cURL 文本。
- 执行器用 `Process` 直接启动 `/usr/bin/curl`，参数通过数组传递，不经过 `/bin/sh`。
- 执行时禁用用户的 `.curlrc`，只允许 HTTP / HTTPS 及同协议范围的重定向。
- 注入应用级 `--max-time 15`，同时使用 15 秒墙钟定时任务覆盖重试期间的等待；超时或取消时先终止进程，约 1 秒后对仍未退出的进程强制结束。
- 进程启动、取消、超时与结束状态由锁保护，避免取消与启动竞态。
- 响应正文、Headers、标准输出和标准错误先写入私有临时目录，避免管道填满造成死锁；正常结束或错误退出后清理临时文件。

### 4.3 JSON 与原生文本交互

- 响应 Pretty 渲染使用自定义 JSON 树，保留键顺序、数字原始字面量与字符串转义，避免大整数因浮点转换失真。
- 各节点共享原始 UTF-8 字节存储，只记录对应范围，不为每层容器复制整份子树文本。
- 根据折叠节点集合生成可见行，左侧只为可见的可展开节点创建原生按钮。
- `NSViewRepresentable` 桥接 `NSTextView` 与 `NSScrollView`，实现全区域聚焦、原生文本选择和滚动。
- JSON 树最大深度为 128（根深度为 0），最大节点数为 20000；超过限制时显示普通响应文本。
- 请求 Body 的「格式化 JSON」使用 `JSONSerialization` 并排序键，与响应侧无损渲染不同；对于必须保持原文字面量或顺序的请求，不应随意格式化。

### 4.4 内嵌应用、图标构建与退出流程

- 同一份源码通过 `BATCH_ACCESS_APP` 编译条件区分入口。工作台使用 SwiftUI Scene，批量访问使用独立 AppKit 事件循环和 `.regular` 激活策略，因此可拥有独立 Dock 图标。
- `KriaWorkbench` 依赖 `KriaBatchAccess` 目标；「Embed Components」复制阶段将完整组件包放入 `Contents/Helpers`，配置 `CodeSignOnCopy`，签名构建时由 Xcode 处理内嵌签名。
- 工作台使用 `NSWorkspace.openApplication` 从自身包内启动组件，设置 `createsNewApplicationInstance = false`，启动中重复点击也会被拦截。找不到组件时显示明确错误，不回退到工作台内的第二个窗口。
- 「Generate Component Icon」构建阶段以 `ICON_EXPORT` 编译同一份图标源码，导出标准 macOS iconset，再用 `iconutil` 生成 `BatchAccessIcon.icns`。临时产物位于 Xcode 的 `TEMP_DIR`，最终资源写入组件包；构建脚本沙箱保持开启。
- 组件目标排除工作台的 `Assets.xcassets`，并由专用基础 Info.plist 指向生成的图标，避免工作台 `AppIcon` 的资产编译元信息覆盖组件图标。运行时图标与包内图标遵循同一绘制逻辑。
- 组件菜单支持隐藏（`⌘H`）、退出（`⌘Q`）、撤销/重做、剪切/复制/粘贴/全选、最小化（`⌘M`）和关闭窗口（`⌘W`）。关闭组件主窗口会退出该组件；隐藏或最小化不会停止执行任务。
- 正常退出返回 `.terminateLater`，先保存请求、取消任务并等待执行收尾，再回复允许退出。删除正在执行的请求时，取消中的任务仍被跟踪直到子进程结束，避免紧接着退出时遗漏清理。强制退出或崩溃不保证执行该流程。

## 5. 数据保存与安全事项

### 保存位置与生命周期

请求数据保存在当前用户的 Application Support 目录：

`~/Library/Application Support/Kria/BatchAccess/requests.json`

可在 Finder 按 `⌘⇧G`，输入 `~/Library/Application Support/Kria/BatchAccess/` 查看。

- 保存格式为 JSON 数组，每个元素包含请求 ID、名称、结构化请求配置、cURL 文本、批量频率、时长及调度方式。
- 请求数据由批量访问组件进程管理，工作台不直接读写请求文件；改为独立组件后，保存位置保持不变，无需迁移原有请求。
- 导入或修改后使用约 400 毫秒防抖自动保存；正常关闭组件窗口或退出组件时，立即保存并取消任务，等待 cURL 子进程结束和临时文件清理后再退出。
- 下次打开批量访问窗口自动加载，并重新校验已保存的 cURL 草稿。
- 保存使用原子写入；目录权限为 `0700`，请求文件权限为 `0600`。
- **不保存响应正文、响应头、执行记录、运行状态和分栏比例**。响应记录只在当前工作区会话中存在，且每轮执行都会替换上一轮记录。
- 保存或读取失败时，工作区底部显示错误提示。

如需手动备份或恢复，请先关闭所有 Kria 实例，再复制或替换该文件。文件不存在时会从空请求集合开始；当前没有云同步、导出管理或多实例写入冲突合并能力。

### 敏感信息与网络操作

- Cookie、Authorization、Token、账号凭证以及 Body 等内容均可能以**明文**保存在 cURL 文本和结构化配置中。当前未接入 Keychain，也没有加密存储。
- 文件权限不是加密；备份、分享命令或截图前应脱敏，不要把真实请求文件提交到仓库。
- 导入不会发送请求，但「发送」与「执行」会真实访问目标服务；批量操作可能反复触发写入、扣费、发券等非幂等行为，只应对有授权的环境使用。
- 「停止」只终止本地调度与连接，不会回滚服务端已执行的操作。
- 忽略 TLS 证书校验会降低连接安全性，仅在可信测试环境中启用。
- 应用当前未启用 macOS App Sandbox。拒绝 Shell 执行和文件型 cURL 参数不等于应用具备完整沙箱隔离。

## 6. 当前限制与排查

### cURL 支持边界

- 一次只导入一条 URL 请求；不支持脚本、多命令、管道、变量展开或命令替换。
- 不支持从本地文件读取 Body、Headers、Cookie，或通过 form-data 上传文件；请粘贴文本字段。
- 不支持的 cURL 参数会显式报错，不会静默丢弃。部分展示类参数会由应用统一处理；同步后的 cURL 不保证与导入文本逐字一致。
- 允许保留的额外选项包括部分超时、重试、代理、认证和 HTTP 协议选项；即使导入更大的 `--max-time`，应用仍执行 15 秒总超时限制。
- 实际选项兼容性依赖系统 `/usr/bin/curl` 的版本；系统不支持的选项可能在发送时失败。

### 响应与资源边界

- 正文最多读取 512 KiB，Headers 和 stderr 各最多读取 64 KiB，stdout 最多读取 1 KiB；超出时在正文中提示截断。
- 上述边界是**响应读取/展示限制**，不是网络下载量或临时磁盘占用上限。响应大小仍按正文临时文件的实际字节数计算。
- 二进制或非 UTF-8 响应显示提示，不提供二进制预览或完整文件下载。
- 被截断、超出 JSON 树限制或包含错误提示的内容可能无法使用 JSON 树模式。
- 最多 10000 条记录不代表低内存占用；大响应、高频率和多请求同时执行会增加内存、CPU、临时磁盘与目标服务负担。
- 随机闹钟的启用状态、间隔设置当前不持久化；应用退出后不会继续提醒。

### 常见问题

| 情况 | 排查方式 |
| --- | --- |
| 发送按钮不可用 | 检查右侧解析提示、URL、引号、Headers 和参数；未完成草稿会保留上次有效预览，但禁止发送 |
| 请求最多等待 15 秒后停止 | 这是单次请求的应用级硬超时策略，包含重试等待；停止不是服务端回滚 |
| 重新运行后没有上一轮响应 | 当前仅保留本轮记录；响应未持久化，请在新一轮发送前复制需要保留的内容 |
| 找不到导入的请求 | 确认是否有保存/读取错误，并检查当前用户 Application Support 下的 `requests.json` |
| 修改后界面没有变化 | 先退出批量访问和工作台，再执行「编译并启动」；普通 `open` 会复用旧实例，不会替换正在运行的代码 |
| 打开组件提示缺少批量访问 | 重新构建 `KriaWorkbench` 或安装完整工作台包，检查 `Contents/Helpers/KriaBatchAccess.app` 是否保留；不要只复制工作台可执行文件 |
| 导入提示一次只能导入一条 URL | 当前已兼容常见续行换行及粘贴空白；确认没有真正的第二条 URL、多个命令或额外位置参数，并检查引号和续行符 |
| Dock 或组件图标仍为旧版本 | 正常退出两个应用后重新编译启动；图标变更会同步生成组件 `.icns`，仅重开窗口或激活旧进程不会加载新绘制代码 |
| 编译提示尚未接受 Xcode 许可 | 打开 Xcode 完成首次配置，必要时在终端执行 `sudo xcodebuild -license` |
| Xcode 报 CoreDevice / CoreSimulator 版本不一致 | 检查 macOS、完整 Xcode、命令行工具和开发目录是否匹配；模拟器相关警告不一定导致 macOS 构建失败，应同时检查退出状态与实际编译错误 |

## 7. 随机闹钟

- 在工作台卡片中开启或关闭提醒。
- 默认随机间隔为 3–5 分钟，最小和最大间隔可分别在 1–120 分钟内调整，最小值不会超过最大值。
- 每轮随机选取等待时间，并显示下一次提醒时刻；修改间隔会影响下一轮抽取，不会重新计算当前已安排的等待。
- 到时显示浮动提醒窗口、闹钟动画和系统提示音；支持手动关闭，或在 10 秒后自动关闭，再安排下一轮。
- 关闭开关会取消等待、关闭提醒窗口并停止提示音。
- 提醒依赖应用持续运行，不是系统后台日历或通知任务。

实现文件位于 `kria/components/randomClock/`：`RandomAlarmController.swift` 管理随机循环，`AlarmPopupCoordinator.swift` 管理弹窗与提示音，`RandomAlarmCard.swift` 提供卡片和提醒界面。

## 8. 海关：iPhone HTTPS 证书信任排障

应用内操作手册入口为海关顶栏的小问号「证书助手与连接指南」，可搜索「iPhone」「完全信任」「-9806」或「非私人连接」。

### 已确认的故障与原因

- **现象**：已启用 HTTPS 解密，部分 iPhone App 请求失败于「客户端 TLS 握手」，报 `connection closed via error`、`OSStatus -9806`；同一设备的 Safari 访问同一 HTTPS 域名时提示「此连接非私人连接」。
- **本次确认的原因**：设备证书信任配置问题，调整信任配置后请求恢复正常。该案例不是已确认的 App 证书绑定问题，也不是 HTTP 正文解析或 OPTIONS 转发问题。
- **判断边界**：`-9806` 仅表示 TLS 连接异常关闭，并不唯一对应证书信任错误。应结合 Safari 验证和实际配置判断，不将所有同码错误归为同一原因。

### 操作步骤

1. 在**当前运行的海关**证书管理页核对 CA 身份与完整 SHA-256 指纹，确认手机安装的是当前 CA，不是同名旧证书。Mac 显示「已信任」不代表手机已经信任。
2. iPhone：`设置 → 通用 → VPN 与设备管理`，确认已安装对应的证书描述文件。
3. iPhone：`设置 → 通用 → 关于本机 → 证书信任设置`，开启**当前 CA 的完全信任**并确认风险。**安装描述文件与开启完全信任是两个独立步骤，不能只完成安装。**受管理设备应遵循 MDM／组织策略，受限时联系管理员。
4. 保持同一代理配置，用 Safari 重新访问出错的 HTTPS 域名。海关出现解密后的 **GET** 记录，即说明该次 TLS 解密成功；页面返回 404 或登录页也可以作为握手验证。
5. 返回 App 重新发起请求。旧的 CONNECT 失败记录不会因信任配置修正而补出正文；CONNECT 的 200 也不代表内部 HTTPS 请求成功。

如果 Safari 仍提示非私人连接，查看证书详情、有效期和设备时间；不要忽略安全警告继续访问，也不要盲目重置 CA。如果曾重置或更换根 CA，需核对新指纹，并重新安装、开启新 CA 的完全信任。如果 Safari 已能解密而 App 仍失败，再排查 App 自定义信任校验、证书绑定及 TLS／应用协议兼容性。
